# Updating the Bot API

Most of package `telegram` is generated from the Bot API reference, so supporting a new Bot API version means regenerating it rather than writing code by hand.

## The pipeline

Telegram publishes the Bot API reference only as an HTML page, with no machine-readable version, so gogram reads that page itself:

```
https://core.telegram.org/bots/api    the Bot API reference, as published by Telegram
        │  internal/cmd/fetchspec: download, keep the documentation part, check it parses
        ▼
internal/apispec/api.html             snapshot of the documentation, checksummed in api.lock
        │  internal/cmd/genapi: check the snapshot against api.lock, parse it, generate
        ▼
*_gen.go, *_gen_test.go               the generated code and its tests
```

1. **Snapshotting**: `internal/cmd/fetchspec` downloads the reference page and keeps only its documentation (`<div id="dev_page_content">`), dropping navigation, scripts and a footer that changes on every request. It parses the snapshot to check that the page layout is still understood, then writes it to `internal/apispec/api.html` and its SHA-256 to `internal/apispec/api.lock`.
2. **Parsing**: package `internal/apispec` reads the snapshot: each method and type is a heading followed by its description, a table of fields and, for unions, a list of members. Result types are read from the method descriptions ("On success, the sent Message is returned"). It validates that every referenced type exists and every method has a result. The rules follow the scraper of [telegram-bot-api-spec](https://github.com/PaulSonOfLars/telegram-bot-api-spec), and produce the same result on the same page.
3. **Generating**: `internal/cmd/genapi` refuses to run if `api.html` doesn't match the lock, then writes the code. Every generated file's header names the Bot API version and its source:

   ```
   // Code generated by genapi from Bot API 10.3 (August 24, 2026) at https://core.telegram.org/bots/api. DO NOT EDIT.
   ```

Telegram's page has no versions to pin, so the committed snapshot is the pin: the same snapshot always generates the same code, and building or using gogram never needs the network or the generator.

## Make targets

| Command | Does |
|---|---|
| `make update-api` | snapshot the reference page, regenerate and test: the way to move to a new Bot API version |
| `make check-api` | fail if the reference page changed since the snapshot, e.g. from a scheduled CI job |
| `make generate` | regenerate the code from `api.html` (same as `go generate ./...`) |
| `make test` | run the tests with the race detector |
| `make lint` | `go vet`, staticcheck and gofmt |
| `make check-generated` | fail if the generated files don't match what `make generate` produces |
| `make check` | `lint`, `test` and `check-generated`: what CI should run |

To move to a new Bot API version:

```
make update-api
git diff --stat          # review: new methods, types and options show up here
git add internal/apispec '*_gen.go' '*_gen_test.go'
```

If Telegram redesigns the page, `make update-api` fails with what it couldn't parse, before anything is written; adjust `internal/apispec/parse.go`.

## What is generated

| File | Contents |
|---|---|
| `telegram/types_gen.go` | every API type, the `Update*` constants, `Update.Type` and `Update.AnyMessage` |
| `telegram/unions_gen.go` | the interface types (`ChatMember`, `InputMedia`, ...) and their decoders |
| `telegram/methods_gen.go` | every method: its request type, constructor, option interface and `Client` method |
| `telegram/options_gen.go` | every `With...` option |
| `update_gen.go` | the `gogram.Update` shortcuts |
| `sandbox/results_gen.go` | the default answers of the fake server |
| `*_gen_test.go` | tests calling every method, option and shortcut, decoding every interface type, and checking the sandbox answers every method |

Hand-written code next to it covers what the spec can't express: the client and request encoder, `InputFile`, `TextData`, `MessageTarget`, `ChatID`, `ReplyMarkup`, the keyboard helpers, and helper methods such as `Message.Command`.

## When the generator stops

The generator fails rather than guess when the spec needs a decision it can't make on its own, for example:

- an option name that would mean different types for different methods (`offset` is a number for `getUpdates` but a cursor string for the gift methods);
- a field accepting several types that no named union covers;
- a generated name clashing with another.

Each error names the table to edit in `internal/cmd/genapi/rules.go`:

| Table | Use |
|---|---|
| `optionNames` | rename the option of one method's parameter, e.g. `sendGift.text` → `WithGiftText` |
| `positional` | make an optional parameter a regular argument, e.g. `editMessageText.text` |
| `unionNames` | name a union the spec writes inline |
| `fieldTypes` | override the Go type of a field |
| `extraOptions` | add a convenience option, such as `WithReplyToMessageID` |
| `chatShortcuts` | choose which methods get a `gogram.Update` shortcut for the update's chat |

## How the spec maps to Go

| Spec | Go |
|---|---|
| `sendMessage`, `MessageId` | `SendMessage`, `MessageID` (initialisms are capitalized) |
| `chat_id` | `ChatID` field of type `telegram.ChatID` (an ID or a username); `int64` in method arguments |
| `Integer` | `int`, or `int64` for user and chat IDs, Unix times and values the spec says can exceed 32 bits |
| `InputFile or String`, `String` fields accepting `attach://` | `*telegram.InputFile` |
| `text` / `caption` with a `parse_mode` | one `telegram.TextData` |
| optional `chat_id`, `message_id` and `inline_message_id` | one `telegram.MessageTarget` argument |
| an object type with kinds | an interface with one struct per kind |
| `MaybeInaccessibleMessage` | `*telegram.Message`; see `Message.IsAccessible` |
| an optional parameter | an option: `With` + the parameter name |
